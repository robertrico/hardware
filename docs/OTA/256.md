## Introduction

This document tracks the journey from a puzzling `memcpy()` failure during an Over-The-Air (OTA) boot process on the RP2040 to a deep understanding of the chip's bootloader architecture, memory initialization, and ROM assumptions. The title, _"256 Bytes,"_ refers to the exact size of the second-stage bootloader loaded by the RP2040 ROM into SRAM5 during cold boot.

## Background

The project implements a dual-partition OTA system:

- **Firmware A (Bootloader)** resides in Slot A and controls OTA download, flash, and jump.
    
- **Firmware B (Application)** resides in Slot B and is launched post-download via a manual jump.
    

## Failure Point

During initial tests, Firmware A successfully jumped to Firmware B, but execution halted almost immediately with a `HardFault`. Inspection in GDB revealed that the crash occurred with [[aeabi]] inside:

```c
__aeabi_double_init();
```

This function failed on the line:

```c
memcpy(&sd_table, rom_table_double, SF_TABLE_V2_SIZE);
```

**Observation:** `rom_table_double` was pointing to a bogus address, and the contents being copied were all zero.

## GDB Trace & Memory Dump

```gdb
(gdb) info registers r0 r1 r2
r0 = 0x1ca
r1 = 0x4653
r2 = 0x80

(gdb) x/8x $r1
0x4653: 0x00000000 0x00000000 0x00000000 0x00000000
```

## Root Cause Hypothesis

1. **ROM Function Pointers Are Assumed:** The RP2040 Pico SDK assumes that `*(uint16_t*)0x1C` points to a valid float dispatch table in ROM (`rom_table_double`). This is only true if the chip was cold-booted through the on-chip ROM.
    
2. **ROM Never Ran:** Because Firmware A manually jumps to Firmware B, the ROM does not run. The ROM is responsible for setting up key pointers:
    
    - `*(uint16_t*)0x18` → ROM function lookup table
        
    - `*(uint16_t*)0x1C` → Float table (`rom_table_double`)
        
    
    These were not valid during runtime.
    

## SDK Source Code Reference

From `pico-sdk/src/rp2_common/pico_double/double_init_rom_rp2040.c`:

```c
memcpy(&sd_table, rom_table_double, SF_TABLE_V2_SIZE);
```

And in `bootrom.h`:

```c
#define rom_hword_as_ptr(rom_address) (void *)(uintptr_t)(*(uint16_t *)(uintptr_t)(rom_address))
```

Which means:

```c
rom_func_lookup = *(uint16_t*)0x18;
rom_table_double = *(uint16_t*)0x1C;
```

## Assembly-Level GDB Snapshot

Before crash:

```gdb
(gdb) x/4x 0x18
0x18: 0x0000001d ...
(gdb) x/4x 0x1D
0x1D: 0x9a880223 ...
(gdb) x/4x 0x9a880223
0x9a880223: 0x00000000 ...
```

This proves that even if `0x18` contains a pointer, the content is junk due to ROM not running.

## Datasheet Confirmation

RP2040 Boot Process (Source: RP2040 Datasheet):

> "Copy 256 bytes from SPI to internal SRAM (SRAM5) and check for valid CRC32 checksum. If checksum passes, assume what we have loaded is a valid flash second stage."

This confirms the first 256B of flash is:

- Loaded to SRAM
    
- Checked via CRC
    
- Executed from RAM (not flash)
    

It also confirms that the ROM configures internal state (e.g., pointers at `0x18`, `0x1C`) which is **not reconstructed** when jumping from user code.

## Conclusions

- The RP2040 bootloader logic is **ROM-dependent**, even after boot.
    
- SDK assumes ROM boot happened, including valid data/function pointer setup.
    
- Jumping to another firmware partition must either:
    
    1. Trigger a watchdog reset and boot fresh
        
    2. Recreate ROM boot conditions manually
